# 差分処理のWeb Worker化 設計

## 1. 背景

正式仕様書8.4「性能改善」は、差分の画素処理を `OffscreenCanvas` と Web Worker に移し、UIスレッドのブロッキングを解消することを求めている。

現行の差分処理は、すべてメインスレッドの同期ループで動いている。
`renderDiffPage` は画素ごとに輝度を判定して着色する二重ループを持ち、位置ズレ許容が有効なときは膨張マスクの生成が加わる。
自動位置合わせが有効なときは、`canvasToGrayF` がページ全体を `Float64Array` へ展開したうえで、FFTによる位相相関を実行する。

既定の解像度を300DPIへ引き上げたことで、この負荷は無視できない水準になった。
A1判を300DPIで描画すると約7,000×9,900画素になり、画素数は約7,000万に達する。
このとき `canvasToGrayF` が生成する `Float64Array` は1枚あたり約560MBであり、新旧2枚で約1.1GBになる。
しかも `bestAlignment` は内部で必ず512×512へ縮小するため、この巨大な配列はほぼ捨てられている。

処理中はメインスレッドが占有されるため、進捗表示は更新されず、ページ送りもキャンセルも効かない。
現行の描画世代（`renderGeneration`）による制御は、古い結果を画面へ反映しないだけであり、計算そのものは最後まで走る。

## 2. 目的

利用者に見える差分の結果を変えずに、次の状態を作る。

- 差分の画素処理と自動位置合わせをWeb Workerへ移し、メインスレッドの長時間占有をなくす。
- 処理中も進捗を表示し、ページ送りなどの操作を受け付けられるようにする。
- 新しい描画が始まったとき、不要になった計算を実際に打ち切る。
- 自動位置合わせのメモリ使用量を、縮小サンプリングの統合によって桁単位で削減する。
- 第2段階のワーカープール並列化を、上位のコードを変えずに追加できる構造にする。

## 3. 対象範囲

### 3.1 対象

- 差分の画素処理（着色、膨張マスク、変更枠検出）のWorkerへの移設
- 自動位置合わせ（`bestAlignment`、`bestQuadrant`、gray化）のWorkerへの移設
- gray化と縮小サンプリングの統合によるメモリ削減
- 描画レーンの分離と、対話操作レーンにおけるジョブの打ち切り
- 段階別および百分率による進捗表示
- 上記に対する単体テスト、統合テスト、E2Eテストの追加と更新

### 3.2 対象外

- pdf.jsによるページのラスタライズのWorkerへの移設
- `OffscreenCanvas` による位置合わせ合成のWorker内実行
- ワーカープールによる並列化とタイル分割
- WebGLシェーダによる差分処理
- 差分の色、しきい値の意味、変更枠の判定基準の変更
- 画面レイアウト、操作方法の変更（進捗表示の文言を除く）

pdf.jsのラスタライズを対象外とするのは、入れ子Workerとフォント描画に不確実性があり、得られる効果に対して変更範囲が大きすぎるためである。
`OffscreenCanvas` による合成のWorker内実行を対象外とするのは、新旧切替モードのキャッシュが実canvasを保持しており、`ImageBitmap` 前提へ作り替える必要があるためである。
どちらも第2段階以降の判断とする。

## 4. Workerとの境界

Workerへは `ImageData` のRGBAバッファを転送可能オブジェクトとして渡す。
転送であるためコピーは発生しない。

メインスレッドに残る処理は次のとおりである。

- pdf.jsによるページのラスタライズ
- 90°回転（`rotateCanvas90`）
- 位置合わせ結果を反映した新版canvasの合成（`renderAlignedNewCanvas`）
- `getImageData` と `putImageData`

これらはいずれもブラウザのネイティブ処理であり、JavaScriptの画素ループはメインスレッドに残らない。

### 4.1 データフロー（差分モード1ページ）

1. メインスレッドが新旧ページをラスタライズし、必要なら90°回転する。
2. 自動位置合わせが有効なとき、新旧canvasを長辺512程度へ縮小し、そのRGBAをWorkerへ転送して `align` ジョブを実行する（第7章）。
3. Workerが位置合わせパラメータ（角度、倍率、平行移動）を返す。
4. メインスレッドが新版canvasを合成する。
5. 旧版と合成後新版のRGBAをWorkerへ転送し、`diff` ジョブを実行する。
6. Workerがgray化、膨張、着色、変更枠検出を行い、RGBAバッファと集計結果を返す。
7. メインスレッドが `putImageData` して描画を完成させる。

### 4.2 転送によるデタッチの扱い

転送後、メインスレッド側の `ArrayBuffer` はデタッチされて読めなくなる。
`prepared.oldImage` と `prepared.alignedNewImage` は差分計算より後に読まれないため、転送して差し支えない。
canvas本体はデタッチされないため、新旧切替モードの表示には影響しない。

なお現行の `toggleCache.oldImage` は保存されるだけで読み出されていない。
300DPI大判では数百MBを死蔵するため、この保持を削除する。

## 5. モジュール構成

### 5.1 新規

| ファイル | 役割 |
|---|---|
| `src/core/image-diff/diff-compute.js` | 差分の画素計算本体 |
| `src/core/alignment/align-compute.js` | RGBAバッファを入力とする位置合わせ |
| `src/workers/diff-worker.js` | Workerのメッセージハンドラ |
| `src/features/visual-diff/worker-lane.js` | Workerレーンの生成、ジョブ管理、打ち切り |
| `src/platform/diff-worker.js` | モジュールWorkerの生成 |

`diff-compute.js` は、現行の `renderDiffPage` の二重ループと `computeChangeBoxesAligned` を1つの関数へ統合する。
両者は同じ判定を行っており、前者が着色を伴う点だけが異なる。
`needsImage` を偽にすると着色を省略し、変更枠だけを返す。
新旧切替モードはこの形で呼び出す。

`align-compute.js` は、RGBAバッファからgray配列を生成する処理と、`bestAlignment`、`bestQuadrant` を提供する。
gray化では長辺512程度への縮小サンプリングを同時に行う（第7章）。

`diff-worker.js` はジョブ種別の振り分けと結果の転送だけを行い、計算ロジックを持たない。

### 5.2 変更

| ファイル | 変更内容 |
|---|---|
| `src/features/visual-diff/visual-renderer.js` | 画素ループを削除し、`dependencies` 経由の非同期関数を待つ |
| `src/features/visual-diff/toggle-renderer.js` | `oldImage` の保持を削除し、変更枠計算を待つ |
| `src/features/documents/page-renderer.js` | `canvasToGrayF` を廃止し、`canvasToRgba` と `downscaleCanvas` を追加 |
| `src/app/create-app.js` | Workerレーンを生成し、描画依存へ注入する |
| `src/features/visual-diff/visual-controller.js` | 描画開始時に対話操作レーンを打ち切り、進捗を表示する |

`visual-renderer.js` はWorkerの存在を知らない。
`dependencies.computeDiff`、`dependencies.computeAlignment`、`dependencies.computeQuadrant` という非同期関数を受け取るだけである。
Workerを差し替えても、テストで同期実装を注入しても、レンダラ側は変更しない。

この変更により、`ensureQuadrant`、`ensureAlignment`、`computeChangeBoxesAligned` が非同期になる。

## 6. Workerレーンと打ち切り

### 6.1 レーンの分離

Workerレーンを2本用意する。

- `interactive` — 画面表示用。新しい描画が始まったとき、実行中のジョブを打ち切る。
- `export` — PNG/PDF出力用。打ち切らない。

PDF出力は全ページを `renderDiffPage` で処理するため、出力中にページを送ると同じWorkerを奪い合う。
レーンを分けることで、出力中の操作が出力を壊さないようにする。

各レーンはWorkerを1つ持ち、ジョブを直列に実行する。
第2段階では、レーン内をNワーカーのプールへ差し替える。
レーンを利用する側のインタフェースは変えない。

### 6.2 打ち切りの方式

打ち切りの定義は「実行中のWorkerを殺す」ではなく、**「その描画に属する以後の全ジョブを無効化する」** とする。
1回の描画はレーンを複数回使う（`quadrant` → `align` → `diff`）。
しかもレーンの手前にはpdf.jsのラスタライズというメインスレッド側のawaitがある。
実行中のWorkerだけを殺す定義では、**まだWorkerに到達していないジョブ**が打ち切りをすり抜ける。

すり抜けは次の順序で起きる。
古い描画R1がラスタライズをawaitしている間に新しい描画R2が始まり、R2の打ち切り要求はレーンが空のため何もしない。
その後R1のラスタライズが先に完了してレーンを占有し、あとから来たR2がレーンを取れずに失敗する。
利用者が見たいページが「レンダリングに失敗しました」で描画されない。

そこでレーンは世代（epoch）を持つ。

- `cancel()` は世代を1つ進め、実行中のジョブがあれば `terminate()` して棄却する。
- `session()` は呼ばれた時点の世代を捉えた実行関数を返す。
- `run()` は、捉えた世代が現行と異なる場合はWorkerを起動せずに `RenderCancelled` で棄却する。

上位は描画1回につき1つの `session()` を取り、その描画のジョブをすべてそこから流す。
これにより、打ち切り以前に始まった描画からのジョブは、レーンへ到達した時点で必ず棄却される。
`run()` はレーンが塞がっている場合も同期的に例外を投げず `RenderCancelled` で棄却し、失敗の表し方を1つに統一する。

第2段階でレーン内をワーカープールへ差し替える際も、この世代の判定はプールへの投入前に行う。

打ち切りは `terminate()` によってWorkerを破棄し、次のジョブのために新しいWorkerを起動する方式とする。

Workerは同期ループの実行中にメッセージを受信できない。
中断フラグを共有する方式は `SharedArrayBuffer` と `Atomics` を必要とし、そのためにCOOPおよびCOEPヘッダの設定が要る。
静的ホストへ配置するだけで動くという運用条件と相性が悪いため採用しない。

`terminate()` は計算のどの段階でも即座に効く。
Workerの再生成はビルド済みモジュールの読み直しであり、数ミリ秒程度で完了する。

打ち切られたジョブのPromiseは `RenderCancelled` エラーで棄却する。
`visual-controller.js` の既存のcatch節は、描画世代が古い場合に例外を握りつぶす作りになっている。
打ち切りはこの流れにそのまま乗る。

## 7. 自動位置合わせのメモリ削減

現行の `canvasToGrayF` は、ページ全体を `Float64Array` へ展開する。
しかし `bestAlignment` は、内部で `downsampleMaskMax` と `resampleToN` によって必ず512×512程度へ縮小している。
したがってフル解像度のgray配列は生成された直後にほぼ捨てられている。

そこで縮小をWorkerへ渡す前に済ませる。
メインスレッドで新旧canvasを長辺512程度のcanvasへ縮小描画し、その縮小後RGBAだけをWorkerへ転送する。
canvasの縮小描画はブラウザのネイティブ処理であり、フル解像度の `getImageData` も不要になる。
`align-compute.js` は、受け取った小さなRGBAをgray化するだけでよい。

300DPIのA1判では、gray配列は1枚あたり約560MBから約2MBになる。
フル解像度のRGBAを取り出す約280MBの一時確保も2枚分なくなる。

この変更により、縮小の経路が変わる。
現行はフル解像度のgrayに対して点サンプリングによる双線形補間を行っており、7,000画素幅から512へ落とす際に強い折り返しが生じている。
変更後はブラウザの縮小フィルタを経るため、この折り返しは減る。
いずれにせよ縮小結果は現行と一致しないため、自動位置合わせのパラメータが現行と厳密には一致しない可能性がある。

`core/alignment/` の既存の単体テストは512×512の配列を直接与えているため影響を受けない。
統合テストとE2Eスナップショットに差分が出た場合は、意図した変化であることを目視で確認したうえで更新する。

## 8. 進捗表示

`postMessage` は同期ループの実行中でも送信できる。
Worker側は行バンド単位（全体の20分の1程度）で進捗を送る。
イベントループへ戻す必要はないため、ループの分割によるオーバーヘッドは小さい。

`dom.status` は次の段階を表示する。

1. `ページを描画中…`（メインスレッドでのラスタライズ）
2. `位置合わせ中…`（`align` ジョブ。自動位置合わせが有効なときのみ）
3. `差分を計算中… 45%`（`diff` ジョブ）

進捗は、描画チケットが現行世代である場合にのみ反映する。
古いジョブの進捗によって表示が巻き戻らないようにする。

## 9. エラー処理

Workerの `error` および `messageerror` は、実行中のジョブのPromiseを棄却する形へ変換する。
棄却された例外は既存の `errorReporter.report(error, "レンダリングに失敗しました")` へ合流する。

同期処理へのフォールバックは持たない。
Workerの生成に失敗した場合は、その旨をステータスへ表示して描画を中止する。
モジュールWorkerは対応環境が十分に広く、二重の計算経路を保守する費用に見合わないためである。

## 10. テスト方針

| 対象 | 方法 |
|---|---|
| `diff-compute.js` | 純関数として直接テストする。既存の差分色、集計、変更枠の期待値を流用する |
| `align-compute.js` | 既知の平行移動と回転を与えて検出できることを検証する。縮小サンプリングを含む新規テスト |
| `worker-lane.js` | 疑似Workerを用い、ジョブ対応、進捗中継、打ち切り時の棄却、再生成を検証する |
| `visual-renderer.js` | `dependencies` へcoreを直接呼ぶ同期アダプタを注入する |
| `diff-worker.js` | ロジックを持たない薄さで担保し、単体テストの対象外とする |
| 実Worker経路 | Playwrightによるブラウザテストで通す |

`visual-renderer.js` の統合テストは、既存の期待値がそのまま通ることを合格条件とする。
差分アルゴリズムの結果を変えないという前提を、ここで担保する。

疑似Workerは `postMessage` と `terminate` を記録するオブジェクトとして実装する。
Workerクライアントの状態遷移だけを検証し、計算結果は検証しない。

## 11. 完了条件

- 300DPIの大判ページでも、差分計算中に進捗表示が更新され、ページ送りが受け付けられる。
- 描画中にページを送ると、実行中のジョブが打ち切られ、新しいページの描画が直ちに始まる。
- PDF出力の実行中にページを送っても、出力が中断されない。
- 自動位置合わせが確保するgray配列とRGBAが、ページ解像度に依存しない大きさになる。
- 差分の色、集計、変更枠の結果が現行と一致する（自動位置合わせのパラメータを除く）。
- 単体テスト、統合テスト、E2Eテストがすべて通る。
