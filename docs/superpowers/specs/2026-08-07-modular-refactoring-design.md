# PDF差分レビューア モジュール分割リファクタリング設計

## 1. 背景

現行アプリケーションは、HTML、CSS、JavaScriptを約191KB、3,348行の `index.html` に収めている。
JavaScriptには124個の名前付き関数があり、PDF読込、画像差分、自動位置合わせ、変更枠編集、テキスト差分、ビューア操作、PNG/PDF出力が同じグローバル状態を共有している。

機能の増加に伴い、非同期描画の競合、キャッシュの無効化漏れ、画面処理と出力処理の状態干渉が起きやすくなっている。
直近の変更枠編集でも、古い描画結果による上書きと、PDF出力による画面用変更枠の汚染を個別に修正している。

このリファクタリングでは、利用者向けの機能と操作結果を変えずに、責務と状態の所有範囲を分離する。
単なるファイル分割ではなく、計算処理、ブラウザ依存処理、画面機能、アプリケーション制御の依存方向を固定する。

## 2. 目的

このリファクタリングの目的は、今後の機能追加と不具合修正を、小さな変更範囲と自動テストのもとで行える構造へ移行することである。

具体的には、次の状態を作る。

- 画像処理、位置合わせ、変更枠検出、テキスト解析をDOMから独立させる。
- 共有状態を用途別に分け、各状態を変更できる機能を限定する。
- キャッシュの生成条件と無効化条件を一か所で確認できるようにする。
- 非同期処理が古い結果を画面へ反映しない共通規則を設ける。
- 画面表示とPNG/PDF出力が互いの一時状態を変更しないようにする。
- 純粋な計算処理、状態遷移、主要なブラウザ操作を自動テストする。
- 静的ホスティングとブラウザ内完結という運用条件を維持する。

## 3. 対象範囲

### 3.1 対象

- Viteを使った開発環境と本番ビルドの導入
- CSSとJavaScriptの複数ファイル化
- Vanilla JavaScriptとES Modulesによるモジュール分割
- アプリケーション状態の用途別分割
- キャッシュ無効化と非同期描画制御の集約
- npmによる既存実行時ライブラリのバージョン固定
- Vitestによる単体テストと統合テストの導入
- Playwrightによるブラウザテストの導入
- READMEと正式仕様書の起動手順およびデプロイ手順の更新

### 3.2 対象外

- 画面レイアウト、文言、色、操作方法の変更
- 差分アルゴリズムの精度変更
- 自動位置合わせアルゴリズムの変更
- 変更枠編集の仕様変更
- テキスト差分アルゴリズムの変更
- React、VueなどのUIフレームワーク導入
- TypeScriptへの全面移行
- Web Worker、OffscreenCanvas、WebGLによる性能改善
- カラー差分、注釈、バッチ処理などの新機能
- 既存実行時ライブラリのメジャー更新

対象外の項目は、モジュール分割後の独立した変更として扱う。

## 4. 変更しない契約

リファクタリング中は、次の利用者向け契約を維持する。

- PDFファイルを外部へ送信しない。
- PDF処理はすべて利用者のブラウザ内で完結する。
- 旧版と新版のページ数、ページ対応、白紙ページの扱いを変えない。
- 削除を赤、追加を青、共通部分をグレーで表示する。
- テキスト差分の削除、追加、変更の色と判定結果を変えない。
- DPI、しきい値、許容差、位置合わせ、回転の設定値と初期値を変えない。
- ズーム、パン、全体表示、等倍、新旧切替の挙動を変えない。
- 変更枠の自動検出、手編集、Undo、破棄確認の挙動を変えない。
- PNG/PDF出力の解像度、凡例、ページ構成を変えない。
- 表示はCSS transformを使い、出力はCanvasの実データを使う分離を維持する。

単一HTMLと `file://` 直接実行は契約から外す。
開発時はViteの開発サーバーを使い、配布時はViteが生成する静的ファイルを使う。

## 5. 採用方式

Vite、Vanilla JavaScript、ES Modulesを採用する。
UIフレームワークは追加せず、現在のDOM構造とCanvas描画を維持する。

JavaScriptは初回リファクタリングでは維持し、公開関数と主要データ構造へJSDocを付ける。
型の導入と責務の分離を同時に行うと差分が大きくなるため、TypeScriptへの移行は別の変更とする。

状態管理ライブラリは追加しない。
現在の状態を用途別のオブジェクトへ分け、各コントローラーが所有する状態だけを更新する。

## 7. 依存方向

依存方向を次の一方向に限定する。

```text
main → app → features → core
                 ↓
              platform
```

- `main` はアプリケーションの生成と起動だけを担当する。
- `app` は状態、DOM参照、機能の組み立て、機能間の調停を担当する。
- `features` は利用者が操作する一つの機能を担当する。
- `core` は入力データから出力データを計算する純粋処理を担当する。
- `platform` はpdf.js、Canvas、ブラウザダウンロードなど実行環境との接続を担当する。

`core` はDOM、Canvas要素、pdf.js、アプリケーション状態を参照しない。
`features` 同士は直接importせず、連携が必要な場合は `app` が呼出順とデータ受渡しを管理する。
グローバル変数は作らず、外部ライブラリもES Modulesとしてimportする。

## 8. 状態の所有範囲

状態は次の領域へ分ける。

| 状態領域 | 保持する値 | 主な更新者 |
|---|---|---|
| `documents` | 新旧PDF、ファイル名、ページ数、ページ対応 | document controller |
| `comparison` | DPI、しきい値、許容差、回転、縮尺、位置合わせ | app coordinator |
| `visual` | 表示モード、描画要求番号、画像キャッシュ、位置合わせキャッシュ | visual controller |
| `boxEditor` | 自動枠、手編集枠、選択、ドラッグ、一時枠、Undo履歴 | box editor controller |
| `textReview` | 抽出結果、ハイライト、描画要求番号、ページ | text controller |
| `visualView` | ビジュアル表示の倍率と移動量 | viewer controller |
| `textView` | テキスト表示の倍率と移動量 | text controller |
| `ui` | 処理中表示、メッセージ、現在の上位モード | app coordinator |

自動検出枠と手編集枠は異なる状態として保持する。
自動検出枠は比較条件から再計算できる派生値であり、手編集枠は利用者が確定した値である。
ドラッグ中の一時枠は確定前の状態であり、ページ切替や描画更新の入口で必ず終了または破棄する。

## 9. キャッシュと無効化

キャッシュは入力条件から構成したキーとともに保存する。
参照時にキーが一致しないキャッシュは利用しない。

無効化規則を `app/invalidation.js` に集約する。
イベントハンドラーが個別のキャッシュを直接削除する構造は残さない。

| 変更 | 破棄する派生状態 |
|---|---|
| PDF読込 | ページ描画、位置合わせ、回転推定、差分、自動枠、手編集枠、テキスト抽出 |
| ページ対応変更 | ページ描画、位置合わせ、回転推定、差分、自動枠、手編集枠 |
| DPI変更 | ページ描画、位置合わせ、差分、自動枠、手編集枠 |
| インクしきい値変更 | 位置合わせ、差分、自動枠、手編集枠 |
| 位置ズレ許容値変更 | 差分、自動枠、手編集枠 |
| 手動位置合わせ変更 | 差分、自動枠、手編集枠 |
| 回転または縮尺変更 | ページ描画、位置合わせ、差分、自動枠、手編集枠 |
| 変更枠最小サイズ変更 | 自動枠、手編集枠 |
| ズームまたはパン | 破棄なし |
| 差分と新旧切替の変更 | 表示用Canvasだけを更新 |

手編集枠を破棄する変更では、現在の仕様どおり利用者へ確認する。
確認でキャンセルされた場合は、比較条件とキャッシュを変更しない。

## 10. 非同期描画

非同期描画は、入力の取得、計算、反映の三段階に統一する。

```text
UI操作
  → Controller
  → 状態更新と無効化
  → 入力スナップショットと要求番号の作成
  → PDF描画
  → 計算
  → 要求番号が最新の場合だけ画面へ反映
```

ビジュアル描画とテキスト描画は別の要求番号を持つ。
PDF再読込時は文書世代も更新し、古い文書に対する処理結果を破棄する。

各処理は `await` の前後で必要な要求番号を確認する。
古い要求はエラーとして表示せず、正常なキャンセルとして終了する。

描画開始後にグローバル状態を読み直さない。
描画開始時に文書、ページ対応、DPI、比較設定、表示モードをスナップショットへ格納し、その値だけを使って計算する。

## 11. 主要データフロー

### 11.1 PDF読込

ファイル選択とドラッグ操作は、同じ `loadDocument(side, file)` を呼ぶ。
document controllerはpdf.jsで文書を読み込み、文書状態を更新した後に関連する派生状態を無効化する。
新旧両方の文書が揃った場合に限り、app coordinatorが現在ページの描画を要求する。

### 11.2 ビジュアル差分

visual controllerはページと比較条件のスナップショットを作る。
page rendererが新旧ページをCanvasへ描画し、alignment coreとimage diff coreが位置合わせと差分を計算する。
change boxes coreが自動枠を計算し、visual rendererが差分Canvasを更新する。
box editor viewは別のオーバーレイCanvasへ変更枠を描画する。

### 11.3 変更枠編集

box editor controllerはポインター座標を画像座標へ変換し、選択、追加、移動、リサイズを状態遷移として処理する。
確定操作の前にUndo用スナップショットを保存する。
画面描画はbox editor viewだけが担当し、編集処理はCanvasへ直接描画しない。

### 11.4 テキスト差分

テキスト差分は次の順で処理する。

```text
PDFテキスト抽出
  → 座標付きトークン
  → XY-cutによる読み順
  → 表領域検出
  → 内容差分
  → ハイライト記述
  → Canvas描画
```

Canvas描画より前の処理はDOM非依存とし、固定入力に対して単体テストする。
text rendererはハイライト記述を受け取り、PDFページ上の矩形として描画する。

### 11.5 PNG/PDF出力

export controllerは画面用Canvasと画面用キャッシュを一時作業領域として使わない。
出力開始時に比較条件と変更枠をスナップショット化し、各ページを出力専用Canvasへ描画する。
凡例と変更枠を値としてimage composerへ渡し、画面側の自動枠と手編集枠へ書き戻さない。

## 12. エラー処理

エラーを利用者操作エラー、処理キャンセル、プログラムエラーに分ける。

- **利用者操作エラー**：PDF読込失敗、テキストレイヤなし、PNG/PDF出力失敗を含む。
- **処理キャンセル**：古い描画要求と古い文書世代の処理を含む。
- **プログラムエラー**：契約外の状態と想定外の例外を含む。

利用者操作エラーは現在の日本語メッセージを維持して画面へ表示する。
処理キャンセルは画面へ表示しない。
プログラムエラーはコンソールへ原因を出し、画面には安全な共通メッセージを表示する。

エラー表示は `app/error-reporter.js` に集約する。
外部テレメトリ、ログ送信、ファイル送信は追加しない。

処理中表示と操作無効化は `try/finally` で解除する。
出力途中の失敗でも、画面状態、表示中ページ、編集枠、ズーム状態を変更しない。

## 13. テスト設計

### 13.1 特性テスト

ファイル分割前に、現行実装の主要な計算結果と操作結果を記録する。
このテストはアルゴリズムの正しさを新たに定義するものではなく、リファクタリング前後の同一性を確認する。

固定PDFに対して、Canvas寸法、差分画素数、変更枠座標、ページ数、出力ページ構成を記録する。
ブラウザや描画環境に依存しやすい全面スクリーンショットの完全一致だけには依存しない。

### 13.2 単体テスト

Vitestで次の純粋処理を検証する。

- 輝度変換とインク判定
- 許容差マスク
- 変更枠の検出、結合、クランプ
- 座標変換と矩形操作
- FFT、位相相関、回転、縮尺推定
- XY-cutの読み順
- 表領域検出とセル差分
- 凡例レイアウト
- キャッシュキーと無効化条件

画像処理には小さな固定配列を使い、ブラウザの描画差をテストへ持ち込まない。

### 13.3 統合テスト

PDF描画、確認ダイアログ、ダウンロードをテスト用実装へ差し替え、次の状態遷移を検証する。

- 古い描画要求がCanvasへ反映されない。
- DPI変更で必要な派生状態が破棄される。
- 手編集枠がある設定変更は破棄確認を通る。
- 破棄確認をキャンセルすると設定とキャッシュが維持される。
- ページ送りでページ別の手編集枠が保持される。
- PNG/PDF出力が画面用キャッシュを変更しない。
- テキスト抽出とテキスト描画の要求番号が競合しない。

### 13.4 ブラウザテスト

Playwrightと小さな固定PDFを使い、次の主要操作をChromiumで確認する。

- 新旧PDFの読込と初回差分表示
- ページ送り、ズーム、パン、全体表示、等倍
- 差分表示と新旧切替
- 自動位置合わせと手動位置合わせ
- 変更枠の追加、移動、リサイズ、削除、Undo
- PNG出力とPDF出力
- テキスト差分モード
- 設定変更が連続した場合の古い描画結果の破棄

FirefoxとWebKitは、モジュール分割完了後の最終回帰で同じ主要シナリオを実行する。

## 14. 依存ライブラリと実行環境

実行時ライブラリは現行バージョンを維持する。

- `pdfjs-dist`：3.11.174
- `jspdf`：2.5.1
- `diff-match-patch`：1.0.5

pdf.js Worker、CMap、標準フォントを本番成果物へ含める。
本番実行時にcdnjsとjsDelivrへ接続しない構成へ移行する。

開発環境はNode.js 22.12以降の22系を基準とする。
Viteの現行公式ガイドはNode.js 20.19以降または22.12以降を要求し、Playwrightの現行公式ガイドはNode.js 22系をサポート対象としているためである。

Vite、Vitest、Playwrightはフェーズ1で採用する版を `--save-exact` でインストールし、完全一致のバージョンを `package.json` と `package-lock.json` に記録する。
依存ライブラリの更新はリファクタリングと同じ変更に含めない。

## 15. 開発と配布

開発時の標準コマンドを次のとおり定める。

```text
npm ci
npm run dev
npm run test
npm run test:e2e
npm run build
npm run preview
```

`npm run test` は監視モードではなく、単体テストと統合テストを一回実行して終了する。
開発者が監視モードを使う場合は別の `npm run test:watch` を使う。

本番成果物は `dist/` に生成する静的ファイル群とする。
`dist/` はGitへコミットせず、Cloudflare Pagesまたは手動配布時にビルドする。

Cloudflare Pagesの設定を次へ変更する。

- Build command：`npm run build`
- Build output directory：`dist`
- Production branch：`main`
- サーバー側処理：なし

手動配布では、`npm ci` と `npm run build` を実行し、生成された `dist/` を静的ホストへ配置する。

## 16. 段階的な移行

### フェーズ1：現行動作の固定

Vite、Vitest、Playwrightを導入し、現在の `index.html` をViteで起動できるようにする。
固定PDFと特性テストを追加する。
このフェーズではアプリケーションコードを分割しない。

### フェーズ2：静的要素の分離

CSSを `src/styles` へ移す。
Base64で重複しているfaviconを既存の `favicon.png` 参照へ変更する。
HTMLの見た目とDOM識別子を維持する。

### フェーズ3：純粋ロジックの分離

幾何計算、変更枠検出、位置合わせ、画像差分、テキスト解析、凡例計算を、単体テストとともに `core` へ移す。
移動前後で同じ固定入力から同じ結果が得られることを確認する。

### フェーズ4：ブラウザ基盤の分離

pdf.js設定、PDF読込、ページ描画、Canvas生成、ダウンロードを `platform` とdocuments featureへ移す。
実行時ライブラリをCDNからnpmパッケージへ切り替える。

### フェーズ5：状態と無効化規則の整理

共有状態を用途別領域へ分ける。
キャッシュキー、無効化規則、描画要求番号を `app` へ集約する。
状態遷移の統合テストを追加する。

### フェーズ6：画面機能の分離

ビジュアル差分、ビューア、変更枠編集、テキストレビュー、PNG/PDF出力を各featureへ移す。
各featureは必要な状態領域と依存だけを受け取る。

### フェーズ7：エントリーポイントの整理

`main.js` を依存関係の組み立てと起動だけにする。
インラインCSSとインラインJavaScriptを削除する。
移行中だけ使った互換処理を削除する。

## 17. 各フェーズの品質ゲート

各フェーズは次の条件を満たしてから次へ進む。

```text
npm run test
npm run test:e2e
npm run build
```

自動テストに加え、実サンプルPDFで読込、差分表示、位置合わせ、変更枠編集、テキスト差分、PNG/PDF出力を確認する。
コード全体への一括フォーマットは行わず、責務の移動と無関係な差分を作らない。

各フェーズを独立したコミットにする。
一つのコミットでは一つの移行目的だけを扱い、失敗時に直前の動作可能な状態へ戻せるようにする。

## 18. 完了条件

次の条件をすべて満たした時点で初回リファクタリングを完了とする。

- 現行の画面、文言、操作、計算結果、出力結果に意図した変更がない。
- `index.html` にインラインCSSとインラインJavaScriptが残っていない。
- `core` がDOM、Canvas要素、pdf.js、グローバル状態に依存していない。
- feature間に直接importがない。
- 主要なキャッシュ無効化と非同期競合が自動テストされている。
- PNG/PDF出力が画面状態と画面用キャッシュを変更しない。
- `npm ci` からテストと本番ビルドを再現できる。
- Cloudflare Pages向けの `dist/` を生成できる。
- READMEと正式仕様書に新しい構成、起動方法、テスト方法、デプロイ方法が記載されている。
- 実サンプルPDFを使った最終回帰確認が完了している。

## 19. 期待する効果

モジュール分割により、修正対象を画像差分、位置合わせ、変更枠、テキスト差分、出力などの機能単位へ限定できる。
レビューでは巨大HTML全体ではなく、対象機能とそのテストの差分を確認できる。

状態の所有範囲と無効化規則を固定することで、別機能の一時状態を誤って変更する不具合を減らせる。
要求番号を使った共通制御により、古い非同期処理が新しい画面状態を上書きする経路を限定できる。

計算処理をDOMから分離することで、自動位置合わせ、変更枠検出、XY-cutを小さな固定入力で検証できる。
この構造は、将来のWeb Worker化、カラー差分、注釈機能を既存画面から独立して追加する土台になる。

初回リファクタリングは利用者向け新機能や性能向上を目的としない。
短期的にはビルド環境とテスト資産の保守コストが増えるが、その後の変更で必要な調査範囲、手動確認範囲、回帰修正を減らす。
